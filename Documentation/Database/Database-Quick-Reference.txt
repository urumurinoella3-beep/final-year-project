📋 ALL TABLES (10)
================================================================================

1. USERS
   - Primary Key: id
   - Unique: email, employee_id
   - Purpose: System users (Admin, HOD, Staff)
   - Key Fields: email, password_hash, role, department

2. DEPARTMENTS
   - Primary Key: id
   - Unique: name
   - Purpose: Organizational departments
   - Key Fields: name, description, is_active

3. ISSUES
   - Primary Key: id
   - Foreign Keys: reported_by, assigned_to, closed_by → users.id
   - Purpose: Core issue tracking
   - Key Fields: title, status, priority, severity, department

4. ISSUE_COMMENTS
   - Primary Key: id
   - Foreign Keys: issue_id → issues.id, user_id → users.id
   - Purpose: Comments and discussions
   - Key Fields: content, is_edited

5. ISSUE_ATTACHMENTS
   - Primary Key: id
   - Foreign Keys: issue_id → issues.id, uploaded_by → users.id
   - Purpose: File attachments
   - Key Fields: file_name, file_path, file_type, file_size

6. NOTIFICATIONS
   - Primary Key: id
   - Foreign Keys: user_id → users.id, issue_id → issues.id
   - Purpose: In-app notifications
   - Key Fields: type, title, message, is_read

7. AUDIT_LOGS
   - Primary Key: id
   - Foreign Keys: user_id → users.id
   - Purpose: Activity tracking
   - Key Fields: action, entity_type, entity_id, ip_address

8. PASSWORD_HISTORY
   - Primary Key: id
   - Foreign Keys: user_id → users.id
   - Purpose: Password reuse prevention
   - Key Fields: password_hash

9. VALIDATION_SESSIONS
   - Primary Key: id
   - Foreign Keys: user_id → users.id
   - Purpose: Data validation tracking
   - Key Fields: file_name, total_records, passed_records, failed_records

10. VALIDATION_ERRORS
    - Primary Key: id
    - Foreign Keys: session_id → validation_sessions.id
    - Purpose: Validation error details
    - Key Fields: row_number, error_type, field_name, description

================================================================================
🔗 RELATIONSHIPS (14)
================================================================================

FROM users TO:
  1. issues (reported_by)        - One user reports many issues
  2. issues (assigned_to)        - One user assigned to many issues
  3. issues (closed_by)          - One user closes many issues
  4. issue_comments (user_id)    - One user writes many comments
  5. issue_attachments (uploaded_by) - One user uploads many attachments
  6. notifications (user_id)     - One user receives many notifications
  7. audit_logs (user_id)        - One user performs many actions
  8. password_history (user_id)  - One user has many password records
  9. validation_sessions (user_id) - One user creates many validation sessions

FROM issues TO:
  10. issue_comments (issue_id)   - One issue has many comments
  11. issue_attachments (issue_id) - One issue has many attachments
  12. notifications (issue_id)    - One issue triggers many notifications

FROM validation_sessions TO:
  13. validation_errors (session_id) - One session has many errors

SELF-REFERENCING:
  14. None

================================================================================
🔄 CASCADE RULES
================================================================================

ON DELETE CASCADE:
  - issue_comments (when issue deleted)
  - issue_attachments (when issue deleted)
  - notifications (when user/issue deleted)
  - password_history (when user deleted)
  - validation_errors (when session deleted)

ON DELETE RESTRICT:
  - issues.reported_by (cannot delete user who reported issues)
  - audit_logs.user_id (cannot delete user with audit logs)

ON DELETE SET NULL:
  - issues.assigned_to (set to NULL when user deleted)
  - issues.closed_by (set to NULL when user deleted)
